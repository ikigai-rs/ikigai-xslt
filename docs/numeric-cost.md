# Numeric adapter: parsed XPath and chart cost

Ledger #2669's fallback applies to **xrust 2.3.0's public API**. The numeric adapter
still uses its bounded source parser. This investigation does not change production
conversion or claim a speedup.

## Why the shared parsed form cannot serve the current stylesheet pipeline

The claim is reproducible: `src/numeric_values.rs` tokenizes and parses precedence
before replacing stylesheet attribute strings. `boolean_values.rs` only classifies
xrust's parsed result and emits ordinary XSLT around the untouched expression.
Numeric adaptation needs edits *inside* expressions, including predicates and AVTs.

An arithmetic AST edit is possible in isolation. Run:

```sh
cargo test --lib standalone_xrust_ast_can_adapt_numeric_operands
cargo test --test numeric_conversion --test xrust_subset
```

The first test parses `/r/v + 1` using xrust, evaluates it on two `v` elements
(`12.5` and `99`), and reproduces the unadapted `NaN`. It then wraps the public
`ArithmeticOperand::operand` ASTs with first-item filtering, string conversion and
normalization, and evaluates the edited AST directly: `13.5`. This experiment does
not use the hand parser. The blocker is installing that AST in a compiled stylesheet.

The dependency source gives these concrete limits (paths below are in xrust 2.3.0;
[versioned source](https://docs.rs/crate/xrust/2.3.0/source/src/)):

- `src/parser/xpath/mod.rs:84`, `parse(&str, Option<N>, Option<NamespaceMap>)`,
  returns only `Transform<N>`. Its `Ok((_, x)) => Ok(x)` discards parser state.
- `src/transform/mod.rs:79` defines a semantic `Transform` enum, without source
  ranges. `ArithmeticOperand` at line 912 has only `op` and `operand`. Literal
  parsers create typed values, and name resolution can discard source prefixes.
  There is no operand-to-source mapping, XPath writer, or general mutable visitor.
  `Debug` emits descriptions such as `Arithmetic 2 operands`, not source syntax.
- `src/xslt.rs:273`, `from_document(styledoc, base, f, g)`, takes an XML node tree;
  `f` parses XML documents and `g` fetches URLs. Neither is an XPath compilation
  callback. It calls its imported XPath `parse` internally, for example for
  globals at line 800 and expression-bearing instructions at lines 865–929.
- `src/transform/context.rs:61`, `Context`, keeps `templates`, `pre_vars` and
  `keys` crate-private. `src/transform/template.rs:17` keeps template `body`
  crate-private too. Public context builders can add hand-built templates but
  cannot recover and edit the bodies generated by `from_document`. Rebuilding
  those would mean implementing the stylesheet compiler here.

A compiler probe accessing those four fields produces four `E0616` errors; the
[recorded output](numeric-private-probe.txt) includes the exact probe. This is an
API limitation, not a claim that an AST cannot represent numeric conversion.

A span-based source edit also cannot be obtained from the returned AST: operand
boundaries and spellings are absent. Matching semantic subtrees back to arbitrary
nested source would still require syntax handling. A complete AST-to-XPath writer
could in principle regenerate source, but xrust supplies none; adding one would
replace the second parser with another substantial implementation of XPath syntax,
including resolved names and all supported function forms. This is not the shared
parser/spans facility sought here.

The bounded parser is retained for that reason, recorded in its module header.
An upstream XPath compilation callback (used for every stylesheet expression and
AVT), a mutable compiled-expression visitor covering templates/globals/keys, or
operand source spans would allow removing it. No upstream fork, dependency patch,
or new XSLT compiler is introduced in this change.

## Chart measurement

```sh
cargo run --release --example numeric-cost -- 1000
```

This offline fixture draws 1,000 circles with arithmetic `cx`, `cy` and `r` AVTs,
using input ordinal strings, count, subtraction, addition, division, multiplication and modulo.
There are nine binary operations, or **18 numeric operand wrappers per point**:
18,000 evaluations of `normalize-space(string((X)[1]))` per chart. Even numeric
literals and intermediate numeric results pay that cost. `count(/chart/p)` is
recomputed per point in both controls; it is part of this workload, not wrapper
cost. These inputs deliberately use scalars that stock xrust already converts
correctly (`string(@i)` supplies each point's ordinal; `position()` outside
predicates is refused by this crate): comparing incorrect unadapted node arithmetic would be misleading.

The example constructs raw and explicitly wrapped versions of the same known
fixture, using no general expression parser. It asserts byte-identical stock raw,
stock wrapped and production crate outputs, and checks the number of circles.
Stock rows isolate the wrappers with the same `RNode` engine and pipeline on both
sides. Crate rows include the existing production adapter and `IdNode` behavior.

All measurements use release builds on the same i7-11800H, Linux x86_64, rustc
1.99.0 machine as [PR 39's RSS measurements](rss-cost.md), now resolving
ikigai-core 0.2.9 (the earlier RSS run resolved 0.2.8), xrust 2.3.0. Five runs are
printed; values below are medians in milliseconds. These are observations, not CI
timing thresholds. Direct xrust and compiled crate calls have no deadline; the
example runs on `limits::on_xslt_stack` and performs no input fetches.

The source is 11,908 bytes. The compact chart template grows from 386 bytes raw
to 926 bytes with explicit operand wrappers; all three paths emit identical
46,946-byte output containing 1,000 circles.

| Stock xrust stage | First raw | First wrapped | Repeat raw | Repeat wrapped |
| --- | ---: | ---: | ---: | ---: |
| Compile | 31.069 | 165.871 | 29.126 | 165.126 |
| Evaluate | 941.953 | 989.169 | 926.292 | 983.843 |
| Transform | 962.936 | 1,016.316 | 958.223 | 1,012.764 |

| Production crate stage (adapter unchanged) | First | Repeat |
| --- | ---: | ---: |
| Compile | 190.556 | 188.091 |
| Reused transform | 1,029.106 | 1,021.209 |

The wrapper control adds 47–58 ms of evaluation per chart (about 5–6%), or an
amortized **2.6–3.2 μs per operand wrapper**, and about 135–136 ms of compilation.
The per-wrapper estimate is the difference of aggregate medians divided by 18,000,
not an isolated microbenchmark or a universal cost. Recomputing count already
accounts for much of this chart's time. Workloads with different expressions or
node selections can have different overheads. A migration that retains every
operand wrapper would not inherently remove that evaluation cost.

Full five-run output: [first measurement](numeric-cost-before.txt),
[repeat measurement](numeric-cost-after.txt).

`stock compile` includes stylesheet XML parse, XPath compilation and teardown.
`stock evaluate` reuses a compiled context and already parsed source, and includes
context setup, evaluation, result construction and teardown. It excludes source
parsing and XML serialization. `stock transform` adds source parsing and XML
serialization. `crate reused transform` includes source validation, parsing,
evaluation, serialization and teardown via `CompiledStylesheet::transform`.
Consequently stock and crate columns have different boundaries and node wrappers;
subtract only stock raw from stock wrapped to estimate the wrapper overhead here.

The before/after files repeat the measurement with the unchanged production
adapter. Only module documentation and a test have been added to that module;
differences between those runs are measurement variation, not an optimization.
The stock raw versus stock wrapped comparison is the before/after conversion
control: it measures the cost of introducing the numeric wrappers.

PR 39's five-run RSS medians were 26.15 / 299.06 / 2,668.73 / 8,197.43 ms for reused
transforms of 100 / 1,000 / 5,000 / 10,000 items, respectively; its 1,000-item source
was 1,024,881 bytes. Those are a different workload, with very little arithmetic,
and should not be used to infer numeric operand cost. Their parsing and evaluation
costs explain why the warm compile cache does not eliminate transform cost; this
chart comparison separately prices the per-operand adaptation.
